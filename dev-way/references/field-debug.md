# 원격 현장 디버깅

상대는 보통 장비 앞에서 휴대폰으로 보고 있다. 그래서 질문은 짧게, 명령은 복사해서 바로 실행되게, 답은 사용자 언어로 한다.

## 1. 받은 것부터 다 읽는다
- 사진: 오류 번호·문구, 켜진 옵션, 화면 아래 상태 줄, 버전. 영상: 프레임을 한 장으로 모아 본다
  (`ffmpeg -i v.mp4 -vf "fps=1/2,scale=400:-1,tile=5x4" t%d.png`).
- 사용자가 이미 한 일·말한 사실을 다시 확인하라고 하지 않는다. 당연한 조언은 신뢰를 깎는다.
  사진에서 본 것이 말과 다르면 "사진에서는 ~로 보이는데" 하고 근거를 들어 묻는다.

## 2. 증거를 요청한다
- 한 번에 1~3개 명령, 각각 "이걸로 무엇을 가르려는지" 한 줄. 명령마다 별도 코드 블록.
- 결과로 갈라질 경우를 미리 적는다(예: "100이면 장비, 1000이면 공유기").
- 출력이 없는 명령은 "성공하면 아무것도 안 나온다"고 알려 준다. 결과가 안 붙어 오면 다시 달라고 한다.
- 자주 쓰는 명령: `linux-commands.md`.

## 3. 재현한다
- 사용자가 보낸 데이터 파일(설정·주문·입력)을 그대로 읽어 임시 시험으로 돌린다. 임시 시험 파일은 끝나면 지운다.
- 시뮬레이터·가상 화면(Xvfb)·가짜 장치로 같은 조건을 만든다.
- 재현이 안 되는 원인(실장비의 감속 시간, 인터럽트 CPU, 모니터 신호)은 "시뮬레이터로는 재현 안 됨"이라고 밝히고, 현장 로그 한 줄로 확정한다.

## 4. 고친다
- 버그는 바로 고친다. 동작을 바꾸는 선택이면 A/B를 보여 주고 고르게 한다(`explain-figure.md`, `ui-preview.md`).
- 실패한 지점·값을 로그에 한 줄 남기는 코드를 같이 넣는다 — 다음에 같은 일이 생기면 증거가 바로 나온다.
- 옛 프로그램을 옮기며 남긴 "그대로 둔 버그"가 원인이면 그 문서에도 바뀐 점을 적는다.
- 관련 시험만 돌리고, 변경 기록에: 현장 증상 → 원인(확정/추정) → 고침 → 확인 → 현장 미확인 항목.

## 5. 보고
- 원인 한 문장 + 확정인지 추정인지.
- 업데이트 전까지 현장에서 할 임시 조치를 명령 블록으로(재부팅하면 풀리는지 표시).
- 릴리스는 묻기만 한다(`release.md`).
