# 코드 쓰기·고치기

게으른 시니어 개발자처럼: 가장 좋은 코드는 쓰지 않은 코드다. 하지만 일은 끝까지 한다.

## 쓰기 전에
- 작업과 그 작업이 닿는 코드를 읽는다. 변경이 닿아야 할 곳을 모두 적는다: 호출하는 곳, 시험, 고정 데이터, 설정, export. 사용자에게 깨질 것(지워지거나 새는 데이터, 동작이 바뀌는 호출)을 확인한다. 이것이 범위다. 추가 기능은 범위가 아니다.
- **데이터 모양부터.** 핵심 타입·자료 구조를 먼저 정하고, 모든 접근 경로를 따라가 본다. 함수 경계를 넘는 변경이면 두 가지 모양을 그려 보고, 상태마다 주인이 하나이고 호출하는 쪽이 가장 적게 알아도 되는 쪽을 고른다.
- 새 요구를 끼워 붙이지 않는다. "처음부터 이 요구를 알고 만들었다면?"을 묻고, 타입·문서·예제까지 같이 바꾼다. 설계는 통째로, 전달은 조금씩.

## 가장 작은 완전한 변경 — 처음으로 되는 것을 고른다
1. 꼭 있어야 하나? 아무도 요청하지 않은 기능·옵션·유연성은 빼고 한 줄로 이름만 적는다. 모호한 요청("X 만들어줘")은 핵심 일만 하는 가장 작은 판.
2. 이 코드베이스에 이미 있나(헬퍼, 컴포넌트, 패턴)? 주변 코드처럼 쓴다.
3. 표준 라이브러리·플랫폼 기능? 쓴다(프로젝트 자체 것이 있으면 그것).
4. 설치된 의존성? 쓴다. 몇 줄 때문에 의존성을 새로 들이지 않는다.
5. 한눈에 읽히는 한 줄? 한 줄.
6. 그래도 아니면 동작하는 최소 코드.

## 규칙
- **빼기 먼저.** 죽은 코드, 남는 검사기, 이름만 남은 참조를 먼저 지우고 만든다. 결과 설계가 조금 더 단순해야 한다.
- 추상화·래퍼·타입 변환·옵션·설정·"나중에 쓸" 코드 금지. 플랫폼이 주는 형태 그대로 값을 다룬다. 코드베이스의 층·인터페이스·관례는 유지.
- **읽는 사람의 부담을 줄인다.** 전달만 하는 층(호출처 하나뿐인 래퍼, 구현이 하나뿐인 어댑터)을 접는다. 상태 범위를 줄인다: 반환 > 변경, 지역 > 필드 > 모듈 > 전역. 동기화 대신 계산. 새 독자가 "X는 어디서 오나, 무엇이 X를 바꾸나"에 30초 안에 답할 수 있어야 한다.
- **도메인을 구조로.** 흩어진 if/불리언 대신 상태 기계, 느슨한 인자 대신 타입, 파일마다 분기 대신 맵·레지스트리·구분 유니온. 불리언 하나가 다른 불리언과 맞춰져야 하면 구조가 빠진 신호. 모양이 분명하고 지역적이면 지루한 코드로 둔다.
- **경계에서만 검사.** 입력·설정·네트워크·외부 API에서 들어올 때 검사·변환·오류 처리를 하고, 안에서는 타입을 믿는다(중복 null 검사 금지). 비즈니스 로직은 순수 함수, 바깥 껍데기는 얇게. 불가능한 상태는 타입이 거부하게.
- **멱등.** 상태를 바꾸는 작업은 몇 번 돌려도, 어디서 끊겼다가 다시 돌려도 같은 결과로 수렴하게: 현재 상태를 읽고 목표와 비교해 차이만 적용. 임시 파일에 쓰고 rename. 남는 잠금·반쯤 쓴 기록은 다음 실행이 알아볼 수 있게.
- **여러 작업자가 같은 걸 쓰면** 먼저 나눈다(작업자마다 파일·키 하나, 읽을 때 합침). 정말 하나여야 할 때만 잠금·단일 작성자.
- **내부 API를 바꾸면** 모든 호출처를 옮기고 옛 API를 같은 번에 지운다(외부 사용자가 없을 때). 호환 층 금지.
- 버그 수정: 고치기 전에 그 함수의 호출처를 모두 찾고, 공통 코드에서 원인을 한 번에 고친다.
- 연관 부분 확인: 여러 파일에 걸친 수정이면 코드 그래프가 있을 때 `graphify affected "<함수>"`로 영향받는 곳을 먼저 보고(`knowledge-graph.md`), 호출처는 grep으로 한 번 더.
- 옮기거나 합치는 코드는 오류 처리·검사를 그대로 가져간다. 크기가 같으면 경계 경우에 맞는 쪽.
- 주석은 코드가 말할 수 없는 "왜"만 한 줄.
- 알고 미룬 한계는 `shortcut: <한계>, <언제 바꿀지>` 주석으로 남긴다(`audit.md`의 목록에 잡힘).
- 사소하지 않은 새 로직(분기, 반복, 파서, 돈·보안, 새 스크립트·앱)에는 작은 시험이나 assert 자체 검사 하나. 사소한 변경엔 없음.
- 사소하지 않은 일은 손으로만 하지 말고 도구를 만든다: 첫 한 단위는 손으로, 그다음 다시 돌려도 안전한 작은 스크립트로(프레임워크 금지).

## 절대 줄이지 않는 것
신뢰 경계의 검사, 데이터 손실을 막는 오류 처리, 보안, 접근성, 실제 하드웨어에 필요한 보정, 사용자가 요청한 것.

## 시험
- 시험은 사용자가 볼 수 있는 동작에 대한 주장이다(반환값, 오류, 읽을 수 있는 상태, 바깥 효과). 내부 함수·호출 순서는 구현이다.
- 상상 두 가지: (a) 동작을 망가뜨리면 시험이 실패해야 한다 — 통과하면 아무것도 증명 못 함(느슨한 단언, 기대값을 시험 대상 코드로 계산). (b) 내부만 바꾸면 통과해야 한다.
- 버그는 값싼 시험 경로가 있으면 실패하는 시험 먼저 → 실패 이유 확인 → 최소 수정 → 통과. 비싸면 가장 가까운 실행 가능한 확인(스크립트, 재현 명령, 화면 캡처). 나쁜 시험보다 시험 없음이 낫다.
- 시험을 잘못된 구현에 맞춰 고치거나 단언을 약하게 하지 않는다. CI를 초록으로 만들려고 실패를 끄거나 재시도·타임아웃만 늘리지 않는다.

## 막혔을 때
- 같은 전제에 기댄 수정이 두 번 같은 데서 실패하면 전제를 의심한다: 전제를 한 문장으로 쓰고, 그 전제가 틀렸다면 달라질 관측을 찾아 먼저 시험한다.
- 상태를 계측해서 실제 값을 읽는다. 깊이 파서 찾은 사실이면, 다음엔 바로 보일 값싼 상시 신호(로그 한 줄)를 제안·추가한다.
