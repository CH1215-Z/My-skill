# 작업 순서 (playbooks)

시작할 때 해당 절의 단계를 할 일 목록에 옮겨 적고 진행한다.

## 버그 수정
1. **직접 재현**한다(시험, 시뮬레이터, 가상 화면, 사용자가 보낸 파일). 재현이 안 되면 조건을 좁히거나 계측한다. 사용자에게는 직접 갈 수 있는 데까지 가 본 뒤에만 묻는다.
2. **원인을 이분 탐색**: 후보 가설을 세우고 실행 증거로 하나씩 지운다. 남은 메커니즘을 증거로 확인한 뒤에 고친다. 변경 이력(git log/blame)도 본다.
3. 고칠 계획. 함수 경계를 넘으면 데이터 모양부터(`code.md`).
4. **같은 조건에서 확인**: 처음 재현이 통과해야 한다. "애매함"이나 다른 조건에서의 통과는 통과가 아니다. 단위 시험은 분기 동작을 보여 줄 뿐 버그가 없다는 증명이 아니다.
5. 값싸면 실패하는 재현 시험을 수정과 같이 남긴다.
6. 답: 무엇이 깨졌나, 원인, 고침, 어떻게 확인했나(전·후 출력).

## 기능
1. 닿는 부분을 따라 읽는다.
2. 모양 정하기(`code.md` 쓰기 전에). 모양이 여러 개로 갈리면 2~3개 시제품을 나란히 비교하고 고른다(UI면 `ui-preview.md`).
3. 순서 점검 네 줄: 먼저 막아야 할 단계 / 서로 독립인 일(파일이 안 겹치면 병렬) / 공유 상태(먼저 나눔) / 가장 작은 안전한 쪼개기. 해당 없으면 "n/a: 이유".
4. 구현 → 실제 화면·동작으로 확인 → 작은 커밋들.
5. 답: 만든 것, 선택과 이유, 열린 결정.

## 리팩터링
1. **동작을 먼저 고정**: 특성 시험·스냅샷·동등성 비교. 타입 검사·린트는 고정이 아니다.
2. 빠진 구조를 이름 짓는다(`code.md` 도메인을 구조로). 결과는 분기·불가능 상태를 줄여야지 간접층을 늘리면 안 된다.
3. 빼기 먼저: 죽은 코드, 호출처 하나 래퍼, 남는 검사기.
4. 작은 동작 보존 단계로, 매 단계 고정 시험 초록. API 모양을 바꾸면 모든 호출처를 옮기고 옛 것 삭제(중간 다리 금지). 이름 바꾸기는 문자열·문서 참조까지 확인.
5. 실물로 같은 동작 증명. 읽는 부담이 줄지 않았으면 되돌린다.

## 성능
1. **기준 측정**부터(실제 데이터·실제 경로). 숫자마다: 무엇을 결정하려는지, 결과를 바꿀 값, 잡음 범위.
2. 코드를 따라 가설. 싼 것부터: (1) 하지 않기 (2) 한 번만 하기 (3) 덜 하기 (4) 나중에 하기 (5) 안 보일 때 하기 (6) 동시에 하기 (7) 더 싸게 하기. 앞의 것으로 목표에 닿으면 멈춘다.
3. 수정마다 다시 측정, 한 번에 하나. "두 배는 왜 안 되나?" — 결과를 묶는 자원·경로를 프로파일·계수로 대고, 숫자가 다른 걸 재고 있을 가능성(오류, 건너뛴·캐시된 일, 안 돈 코드)을 지운다. 반복 차이가 효과보다 크면 멈춘다.
4. 답: 전 숫자, 후 숫자, 차이, 측정 방법.

## 읽기만 하는 조사 ("어떻게 동작해?", "왜 이렇게 돼?")
1. 질문에 해당하는 코드를 따라 읽는다. "왜"는 커밋·변경 기록에서 이유를 찾는다.
2. 이미 기록된 사실(CLAUDE.md, 문서)이 있으면 그것부터 — 다시 분석하지 않는다.
3. 답: 개요 / 핵심 개념 / 동작 순서 / 어디에 있나 / 함정. 선택 질문이면 추천 + 장단점 표. 동작 설명은 그림이 낫다(`explain-figure.md`).
4. "확실해?"에는 진짜 판단을 준다. 아니면 아니라고.
