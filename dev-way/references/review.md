# 리뷰 (변경 하나)

호출받을 사람처럼 본다. 중요도: 맞다 > 안전하다 > 실제 부하를 견딘다 > 위험한 코드에 시험이 있다 > 빠르다 > 군더더기 없다. 사용자가 요청한 보고서이니 빠짐없이.

## 1. 먼저 이해
- 대상: 사용자가 말한 것(커밋 안 된 변경, 브랜치, PR, 파일). 없으면 커밋 안 된 변경, 없으면 마지막 커밋.
- diff를 읽고, 닿는 코드를 읽는다: 바뀐 함수의 호출처, 그 함수가 부르는 것, 시험, README.
- 실제 흐름을 따라간다: 데이터가 어디서 들어와 무엇이 저장되고 무엇이 나가나.
- 시그니처·반환값·동작이 바뀌면 모든 호출처를 grep.
- 예상 부하(혼자 쓰는 스크립트 vs 여러 사용자·프로세스)를 찾아 그 기준으로 판단하고, 어떤 부하를 가정했는지 쓴다.

## 2. 찾을 것
1. 버그: 틀린 결과, 충돌, 빠진 경계(빈 값, 0, 마지막, 반올림, 시간대), 깨진 호출처, 공통 함수는 둔 채 한 호출처만 고침.
2. 위험: 보안(주입, 약한 난수, 비밀값, 입력 검사 없음), 데이터 손실(오류 삼킴, 쓰기 순서, 트랜잭션 없음).
3. 규모: 확인-후-쓰기 경쟁, 모든 프로세스가 같은 일, 계속 자라는 메모리, 항목마다 쿼리, 큰 입력의 O(n²).
4. 빠진 시험: 위험한 새 로직에 깨지면 실패할 시험이 없음. 좋은 시험 하나면 된다.
5. 속도: 큰 느려짐은 문제, 작은 이득은 제안.
6. 군더더기: 지울 것 / 이미 있는 것 재사용(경로) / 표준·플랫폼 / 안 쓰는 추상화 / 함께 바뀌어야 하는 복사본 합치기 / 여러 일을 섞은 함수 나누기(일 단위로).

## 3. 이 변경이 다른 데를 깨나 (blast radius)
- diff 밖을 본다: 라이브러리 소스(고정 버전), 타이밍, 저장·전송 형식(JSON·DB·파일), 같은 바이트를 읽는 다른 언어·프로그램, 기능 스위치, 세 단계 떨어진 코드.
- **이 변경이 안전한 이유가 되는 사실 하나**를 찾아 증명 수준을 올린다: (1) 말만 함 = 가치 없음 (2) 파일:줄 인용 (3) 나쁜 경우를 따라가 봄 (4) 실제 코드로 도는 작은 스크립트·시험(틀리면 크게 실패) (5) 실행 중인 앱에서 재현. 보통 (4)까지.
- 큰 변경은 "깨 보기"를 한다: 이 변경을 깨는 실행을 찾게 하고, **돌려서 증명된 것만** 남긴다. 아무것도 못 찾는 것도 정상 결과.

## 4. 보고 전에 확인
- 모든 지적에 구체적 경우: "이 입력·상황 → 이 틀린 결과". 없으면 지적 아님.
- 줄을 다시 읽어 확인(호출처가 실제로 있나, 값이 정말 비나, 정말 안 쓰나).
- 한계를 적은 `shortcut:` 주석은 결정이지 지적이 아니다(부하가 이미 넘었으면 예외).
- 가장 작은 고침, 지우는 고침 우선. 취향·"고려해 보세요"·막연한 걱정 금지.

## 5. 출력 (쉬운 말, 사용자 언어)
`이 변경이 하는 일:` 2~3문장. 그다음 세 묶음(빈 묶음 생략): **꼭 고칠 것**(버그·보안·데이터 손실·부하에서 깨짐) / **고치면 좋은 것**(시험 없는 위험 코드, 실제 느림, 중복, 섞인 함수, 없어야 할 코드) / **있으면 좋은 것**.
지적에 번호(묶음을 넘어 이어서). 각 지적 네 부분: **무엇인지 / 문제 / 고침 / 넘어가면**.
끝: `판정: 내보내도 됨.` 또는 `판정: 1, 3 먼저.` / 군더더기가 있으면 `줄일 수 있는 줄: -N` / `확인 못 함:` 한 줄.
아무것도 없으면 `이 변경이 하는 일:` + `문제 없음. 내보내도 됨.` + 무엇을 봤는지 한 줄. 코드는 바꾸지 않는다.
