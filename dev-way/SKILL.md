# dev-way

이 스킬은 본문(공통 규칙 + 길 안내)과 `references/`의 상황별 문서로 되어 있다. 본문은 늘 지키고, 일의 종류가 정해지면 해당 문서 하나만 읽는다.

## 늘 지키는 것

1. **사용자 언어로, 짧게.** 요약·재시작 뒤에도 같은 언어. 첫 답에서 목표와 "가장 작은 변경"을 한 줄로 다시 말하고 바로 시작한다. 끝에 한두 줄: 하지 않은 것·확인 못 한 것·위험.
2. **가장 작은 완전한 변경.** 새 코드는 최소로, 일 자체는 끝까지(호출하는 곳·시험·설정까지). 자세한 규칙은 `references/code.md`.
3. **실물로 확인.** "빌드됨", "아마 될 것"은 확인이 아니다. 실제로 돌리고, 값을 읽고, 화면을 찍는다. 못 했으면 못 했다고 쓴다.
4. **원인을 고친다.** 증상이 나온 곳이 아니라 처음 잘못된 곳. 재현부터. 가드·재시도·삼킨 오류로 덮지 않는다.
5. **주장에 꼬리표.** 확정(돌려서 봄) / 추정 / 모름을 구분한다. 증거 없는 주장은 가설이다.
6. **되돌릴 수 있는 일은 묻지 말고 하고, 되돌릴 수 없는 일은 반드시 묻는다.** 강제 푸시, 배포·릴리스, 데이터 삭제, 외부로 보내는 메시지, 비용이 드는 대량 실행은 사용자가 분명히 말했을 때만. UI·동작을 바꾸는 선택은 예시를 보여 주고 고르게 한다.
7. **기록을 남긴다.** 일 하나 = 커밋 하나 + 변경 기록 한 항목. 사용자 결정과 확정된 사실은 CLAUDE.md에. (`references/memory.md`)
8. **같은 지적을 두 번 받으면 구조로 고친다.** 규칙 글을 늘리지 말고 검사·스크립트·시험으로 만든다.

## 명령 없이 자동으로 할 때의 선 (모든 부분이 상황에 맞으면 저절로 동작한다)
- **그냥 한다**: 읽기, 검색, 시험·빌드 실행, 재현, 화면 캡처, 그림 그리기, 작업 기록·커밋, 리뷰 보고서, 이미 있는 그래프에 질문, 설치된 분석 도구로 읽기만 하는 분석.
- **한 줄로 알리고 한다**: 버그 수정(원인과 고칠 곳을 먼저 한 줄), 실패 지점 로그 추가.
- **묻지 않고 설치한다(사용자가 한 번에 허락, 2026-11-26)**: 아래 "필요한 프로그램" — 작업을 시작할 때 없으면 `sh scripts/setup_tools.sh`를 그냥 실행하고 결과 한 줄씩만 알린다.
- **먼저 묻는다(한 번)**: 그 밖의 프로그램·MCP 설치나 설정 쓰기, 문서·이미지가 많은 그래프 새로 만들기(토큰·시간), UI·동작을 바꾸는 선택(예시 먼저), 의존성 추가, 큰 범위 리팩터링.
- **분명히 말했을 때만**: 릴리스·배포, 강제 푸시, 데이터 삭제, 외부로 보내는 메시지, 분석 대상 실행·변조.
- 같은 일을 하는 다른 스킬(ponytail 등)이 같이 켜져 있으면 이 스킬이 길을 정하고, 그 스킬은 해당 문서가 가리킬 때만 쓴다 — 같은 규칙을 두 번 적용하지 않는다.

## 필요한 프로그램
디자인(impeccable), 지식 그래프(graphify), 빌드된 프로그램 분석(rea)은 프로그램이 있어야 제대로 돈다. **새 세션에서 이 스킬을 처음 쓸 때 `sh ~/.claude/skills/dev-way/scripts/setup_tools.sh`를 묻지 않고 실행한다** — 없는 것만 설치한다: impeccable(자기 저장소 github.com/pbakaus/impeccable에서 복사, 이 저장소엔 포함하지 않음), graphify(uv + 스킬), rea(`npx rea-agents setup --yes --all-detected`). 상태만 볼 때는 `--check`. 새로 깐 스킬은 다음 요청부터, rea 같은 MCP 도구는 다음 세션(또는 재시작)부터 보인다. 이미 있는 craft-anything MCP는 rea 대신 써도 된다.

## 레벨 (`/dev-way lite|full|ultra`)
- **lite**: 요청대로 만들고, 더 작은 방법이 있으면 한 줄로 알려 고르게 한다.
- **full**(기본): 아래 문서의 규칙 그대로.
- **ultra**: 만들기 전에 요청 자체도 따진다. 필요가 정당화하지 못하는 부분은 반박한다.

## 길 안내 — 일의 종류에 맞는 문서 하나를 읽는다

| 상황 | 읽을 문서 |
|---|---|
| 코드 쓰기·고치기(모든 코딩의 기본) | `references/code.md` |
| 버그 수정 / 기능 / 리팩터링 / 성능 / 읽기만 하는 조사 | `references/playbooks.md` 의 해당 절 |
| "리뷰해줘", 커밋·PR 점검, 변경이 다른 데를 깨는지 | `references/review.md` |
| 저장소 전체 점검, 지울 것 찾기, 미뤄 둔 일(shortcut) 목록 | `references/audit.md` |
| 릴리스·배포·설치 파일·ISO | `references/release.md` |
| 현장·고객·다른 PC의 문제(사진·영상·로그) | `references/field-debug.md` (+ `linux-commands.md`) |
| UI를 바꾸기 전 실제 화면 예시, 화면 속도 | `references/ui-preview.md` |
| 동작·선택지를 그림으로 설명 | `references/explain-figure.md` |
| 커밋·변경 기록·CLAUDE.md, 긴 작업의 결정 기록 | `references/memory.md` |
| 화면·웹 디자인 품질(새 화면, 다듬기, 디자인 리뷰) | `references/design.md` |
| 빌드된 프로그램·앱·펌웨어·캡처 분석(소스가 아닌 것) | `references/binary-analysis.md` |
| 큰·낯선 코드베이스 구조 질문, 문서↔코드 연결 | `references/knowledge-graph.md` |
| 문서·PR 글·커밋 메시지·답 문장 다듬기 | `references/writing.md` |

여러 개에 걸치면 가장 앞 단계 것부터(예: 현장 버그 → field-debug → playbooks의 버그 수정 → release).

## 스크립트 (`scripts/`)
- `wait_release.sh owner/repo tag [초]` — GitHub 릴리스 결과물이 올라올 때까지 확인
- `xvfb_app.sh N WxH -- 명령` / `x.sh N click|type|key|shot …` — 가상 화면에서 앱 실행·조작·캡처
- `render.js in.html out.png 폭 높이` — HTML/SVG 그림을 PNG로(Playwright)
- `geom.py` — 설명 그림용 오프셋·교점 계산
- `setup_tools.sh [--check]` — impeccable·graphify·rea 중 없는 것 설치(`--check`는 상태만)
